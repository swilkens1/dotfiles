# dotfiles

Bare-repo dotfiles for bash, vim, git, AWS CLI, and Claude Code CLI. Runs on:

- **Windows** — MSYS2 UCRT64 (recommended) or Git Bash
- **Linux** — any bash-capable distro
- **macOS** — bash from Homebrew

## Bootstrap a new machine

Prereqs (Windows): install MSYS2 first (`winget install MSYS2.MSYS2`), then launch the **UCRT64** shell. Prereqs (Linux/macOS): just `git`, `curl`, `bash`, `vim` on PATH.

```bash
curl -fsSL https://raw.githubusercontent.com/swilkens1/dotfiles/master/bootstrap.sh | bash
```

Then complete the manual steps the script prints (corp CA if applicable, `aws configure sso`, work email in `.gitconfig-work`).

## Daily workflow

```bash
config status                       # see tracked changes
config add -f ~/path/to/new/file    # start tracking a new file (-f required: info/exclude=*)
dotsync                             # pull, show diff, commit, push
```

`config` is an alias for `git --git-dir=$HOME/.cfg/ --work-tree=$HOME`. The `*` in `info/exclude` means nothing is auto-tracked — you must explicitly `-f` add every new file. `info/exclude` is per-clone and `bootstrap.sh` re-creates it with an explicit deny list on top of `*`.

| `bootstrap.sh` | This file's setup script |
| `README.md` | This file |

## What's deliberately NOT tracked

- `.aws/config` — profile/SSO layout is per-employer; run `aws configure sso` on each machine
- `.aws/credentials` — restore manually or use SSO
- `.aws/corp-ca.cer` — corporate CA bundle, if any; per-machine (see "Corporate machines" below)
- `.aws/sso/`, `.aws/cli/cache/` — runtime caches, regenerated by `aws sso login`
- `~/.ssh/` — generate fresh keys per machine
- `.claude.json` — per-machine state (machineID, userID, onboarding flags, counters)
- `.claude/settings.local.json` — machine-specific overrides (e.g., `CLAUDE_CODE_GIT_BASH_PATH`); create empty as needed
- `.claude/auth.conf` — employer-managed SSO config, auto-generated on managed work machines
- `.claude/{sessions,projects,cache,backups,shell-snapshots,ide,session-env,file-history}/` — runtime state, transcripts, caches

Since `info/exclude=*` is deny-by-default, the above just documents things that *look* trackable but shouldn't ever be `config add -f`'d. bootstrap.sh re-writes `info/exclude` with the same explicit denies.

## Portable HOME (MSYS2 vs Git Bash on Windows)

On MSYS2, `$HOME` is `/home/$USER` (`C:\msys64\home\$USER`). But Windows-native binaries (`aws.exe`, `mise.exe`, `kubectl.exe`, `docker.exe`, `claude.exe`) resolve home via `%USERPROFILE%`, not `$HOME`. To keep both worlds seeing the same config files, `bootstrap.sh` creates **NTFS directory junctions** (via `mklink /J`) at `$HOME` pointing back to `%USERPROFILE%`:

- `~/.aws`, `~/.kube`, `~/.docker`, `~/.claude`, `~/.config`, `~/.ssh`, `~/.local`

Junctions need no Admin rights or Developer Mode. To rollback, run `cmd //c 'rmdir C:\msys64\home\$USER\.aws'` — this removes the junction only, not the target contents. **Never** `rm -rf` a junction from bash; it follows the link and deletes the target.

On Git Bash (Windows) or Linux/macOS, `$HOME` already resolves the way native tools expect, so junctions are unnecessary (and `bootstrap.sh`'s junction block is a no-op).

## Cross-platform tool install strategy

`bootstrap.sh` uses OS-specific branches:

| Tool | Windows | Linux | macOS |
|---|---|---|---|
| **terraform, tflint, kubectl, shellcheck, trivy, ...** | mise | mise | mise |
| **AWS CLI v2** | winget (`Amazon.AWSCLI`) | official bundled installer | brew (`awscli`) |
| **Session Manager Plugin** | winget (`Amazon.SessionManagerPlugin`) | `.deb` for apt / manual for others | brew (`--cask session-manager-plugin`) |
| **Git** | winget (`Git.Git`) — has GCM bundled | package manager | brew or Xcode CLT |
| **Docker Desktop** | winget (`Docker.DockerDesktop`) | manual (Docker Engine) | brew (`--cask docker`) |
| **Multipass** | winget (`Canonical.Multipass`) | `snap install multipass` | brew (`--cask multipass`) |
| **MSYS2 itself** | winget (`MSYS2.MSYS2`) — manual prereq before bootstrap | — | — |

All winget calls in bootstrap are idempotent (skipped if already installed). Failures print a warning and continue.

## Corporate machines

If your work machine sits behind a corporate MITM proxy that intercepts HTTPS with a private CA, that CA needs to be on the trust chain for `aws.exe` to reach AWS. Two options:

1. **Filename convention:** drop the cert at `~/.aws/corp-ca.cer`. `30-aws.sh` finds it and exports `AWS_CA_BUNDLE`.
2. **Env-var override:** export `CORP_CA_BUNDLE=/some/path` from a local-only `~/.bashrc.d/9*.sh`. `30-aws.sh` prefers that if set.

The corp CA file itself is NOT tracked (it identifies your employer, is machine-specific, and isn't useful on personal machines). Personal machines simply won't have the file and `30-aws.sh`'s guard silently skips setting `AWS_CA_BUNDLE`.

If your employer ships a managed Claude Code CLI install with `.claude/auth.conf` for SSO, that file also lives untracked and is created by whatever provisioning your employer does. Nothing tracked references it.

## Claude Code

Claude Code CLI keeps its config under `~/.claude/`. On Windows the CLI resolves this via `%USERPROFILE%`, not `$HOME` — the MSYS2 junction (above) handles that.

### settings.local.json — machine-specific escape hatch

Claude Code merges `settings.local.json` on top of `settings.json`. Bootstrap doesn't create it (you make one only if you need overrides). Common use on Windows:

```json
{
  "env": {
    "CLAUDE_CODE_GIT_BASH_PATH": "C:\\msys64\\usr\\bin\\bash.exe"
  }
}
```

Claude Code auto-detects Git Bash when Git for Windows is installed; only set this if detection isn't firing (check by running a shell command in a Claude session and seeing which shell handles it). Point at `"C:\\Program Files\\Git\\bin\\bash.exe"` if you're on Git Bash instead of MSYS2. Restart Claude Code after editing — env vars load at startup.

### Hooks

`SessionStart` runs `check-archive-size.sh` (warns if `~/claude-archive` > 500 MB). `SessionEnd` runs `archive-session.sh` (copies the session's `.jsonl` transcript there). Both honor `$CLAUDE_ARCHIVE_DIR` if you want the archive somewhere else per machine — export it from a local-only `~/.bashrc.d/9*.sh`.

### VS Code sync

VS Code's built-in Settings Sync (sign in with GitHub/MS) handles `settings.json`, keybindings, extensions, snippets across machines. Recommended over trying to track `%APPDATA%\Code\User\` in this repo — no overlap and less to manage. Only sync the "Extensions" category if you want dotfiles to stay authoritative for the rest.

## Adding new modules

Drop a file in `~/.bashrc.d/` using the load-order prefix convention:

- `10`-`19`: prompt / shell behavior
- `20`-`29`: platform / OS wrappers
- `30`-`39`: AWS
- `40`-`49`: SSM / per-tool helpers
- `50`-`59`: dotfiles management
- `60`-`69`: tool / version managers (mise)
- `70`-`79`: kubectl
- `80`-`89`: terraform
- `90`+: local-only overrides (not tracked)

Then: `config add -f ~/.bashrc.d/NN-name.sh && dotsync`.

## Managing tool versions (mise)

`bootstrap.sh` installs [mise](https://mise.jdx.dev) into `~/.local/bin` and hydrates the global toolchain from `~/.config/mise/config.toml`. On Windows it pulls the bare `.exe` from GitHub releases because corporate AV can block winget's extract step.

Globals live in `~/.config/mise/config.toml` (tracked). Per-project pins live in `.mise.toml` or `.tool-versions` checked into each repo.

```bash
mise use -g terraform@latest tflint@latest    # set + install globals
mise use terraform@1.9.5                      # pin in current project (creates .mise.toml)
mise install                                  # install everything from config(s)
mise upgrade                                  # bump floating pins
mise outdated                                 # show what's behind latest
mise self-update                              # upgrade mise itself
```

`60-mise.sh` runs `eval "$(mise activate bash)"` on Linux/macOS so a `cd` into a project with a different pin swaps versions on the next prompt. On Windows/MSYS2 it uses mise's shim mode (the activate output is Windows-format PATH that bash can't parse) — same behavior, different mechanism.

When you change globals, commit them: `config add -f ~/.config/mise/config.toml && dotsync`.

## Switching to Neovim later

When you install nvim, create `~/AppData/Local/nvim/init.vim` (Windows) or `~/.config/nvim/init.vim` (Linux) containing:

```vim
set runtimepath^=~/.vim runtimepath+=~/.vim/after
let &packpath = &runtimepath
source ~/.vimrc
```

Nvim then reuses your existing `.vimrc` and plugins as-is. Port to `init.lua` + lazy.nvim incrementally from there.
